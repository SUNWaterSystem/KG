Week16：CCR KG 工作流学习记录

整理日期：2026-10-28。依据当前项目代码、Wang 首轮记录和 Sun 第二篇论文的实际运行记录核对。

这份记录沿用 Week14–15 的概念和 Property Graph / Neo4j 路线，重点解释系统怎样运行，并区分当前实现与后续计划。

我们在建设一个受 ontology 约束、能够追溯原文的文献到知识图谱工作流。模型负责提出候选知识，程序负责检查和组织数据，领域人员负责正式确认。图谱保留条件、来源和处理版本，后续可以继续加入论文。

阅读顺序：整体流程 → 证据结构 → 任务生成 → 模型输入 → 实际输出与验证 → 通用化改进。代码与解释采用左右对照表，按行从左向右阅读。另附离线 HTML 阅读版，流程图直接显示，无需启动 KG 服务。

1. 整体流程：输入什么，经过什么，输出什么

1.1 输入与分工

输入或组件作用当前状态

2. 文档解析与证据：先知道“这段话来自哪里”

2.1 parse.py 负责什么

目的：把 PDF 原始证据持久化，使后续候选能回到具体文档、页码和区域。

功能当前怎样实现需要注意
文件识别与缓存保存 PDF，计算 SHA-256，记录解析器版本并复用缓存同名文件不一定是同一版本
Document Parsing使用 pdfplumber 提取原生文字，按预设左右两栏读取目前是固定双栏策略，尚非自动版面识别
Document Chunking按行累积，约 1700 字符切成一个文本 Span字符限制不等于 Token 预算，也不是按章节语义分块
Evidence Management登记 ID、PDF 页码、bbox、字符偏移及角色bbox 是登记区域，可能覆盖较大范围，不保证精确到句子
表格区域针对 Wang 的 Table 1–3 使用页码和标题等布局规则尚无通用表格检测及行列重建能力
table3_audit()从已登记的 Table 3 文本读出预期 42 个数值记录后续由 compare_table3() 与候选逐项比较
render_evidence()渲染原始 PDF 页，并标出已登记 bbox辅助人工核验，不是重新抽取图片知识

当前一个 parse.py 同时承担 Parsing、Chunking 和 Evidence Management；三个问题相关，但后续可以分别改进。

2.2 Span：最关键的证据对象

Span 是一个带来源信息的文本或表格片段。下面是当前正文证据登记代码，左边为 Python 字典的各行，右边逐项解释；它不是已经填好数值的 JSON。

Python：正文证据 record含义
record = {开始登记一个证据对象
"source_span_id": span_id,证据的唯一 ID，后续 Claim 通过它引用原文
"document_version": sha,原始 PDF 文件字节的 SHA-256 指纹，不是论文内容摘要
"parser_id": parser_id,由解析器版本和 pdfplumber 版本计算的标识
"page": number,从 1 开始的 PDF 实际页序，不一定等于期刊印刷页码
"bbox": region["bbox"],PDF 区域坐标 [x0, top, x1, bottom]，单位为 PDF point
"column": region["column"],栏号；当前 1 为左栏，2 为右栏
"start_char": source_offset,片段在当前页拼接文本中的起始字符位置
"end_char": source_offset + len(text),结束字符位置，不包含该位置
"text": text,从 PDF 解析并登记的证据文本，仍需关注断行、公式等解析误差
"role": role,此处为正文 body 或参考文献 references
"kind": "text"此处证据类型为原生文本；表格区域另用 kind="table"
}一个完整的正文证据记录

表格 Span 还包含 table_number；其字符偏移基于独立的表格区域文本，记为 offset_basis="table-region-text"，不能直接当作整页文本偏移。

2.3 pages、spans、coverage 的关系

数据保存什么回答的问题
pages每页拼接的解析文本及页面尺寸这一页解析出了什么？
spans文本块或表格区域及其来源信息这段证据是什么，来自哪里？
coverage每个 Span 的处理状态与原因这段证据是否被送入处理，处理到哪一步？

parse_document() 的结果还保存 document_id、sha256、parser_id、parser_version、原 PDF 路径和 limitations，最终缓存为 JSON。

2.4 Coverage：处理覆盖记录，不是知识准确率

初始登记代码（Python）解释
"source_span_id": span_id,对应哪一段证据
"page": number,来自哪一页
"state": "excluded" if role == "references" else "pending",参考文献初始排除，其他证据等待处理
"reason": ...保存排除或处理状态的原因；此处省略具体表达式
状态当前代码中的意义谁更新
pending初始登记，尚未完成该任务阶段parse.py 初始化
excluded不进入当前抽取范围，如参考文献parse.py 初始化；pipeline.py 也会收尾标记未使用区域
completed该证据所属任务已返回并经过本轮验证步骤pipeline.py，不表示每条候选已通过或经过专家确认
failed运行异常时，对仍待处理证据记录失败原因pipeline.py，不是论文“没有结果”

原笔记说“parse.py 只生成初始状态”是对的；但完整工作流已经由 pipeline.py 更新后续状态。目前没有单独的 Span 状态 validated。Coverage 完成也不证明所有知识都已抽全。

3. Task Planning：Wang 与 Sun 的任务分别怎样生成

3.1 Wang：明确写在代码中的四类任务

Wang 研究七种硅酸盐矿物与 GLDA。当前 Codex 路径识别到 Wang DOI 且存在 Table 1–3 后，执行专用分支。

任务名提供的证据提取范围

3.2 Sun：通用正文切块，不要求使用 Wang Profile

问题：上传另一套 `vocabulary`、`rules` 和 `schema` 后，为什么 Sun 仍然有任务？

因为“怎样分任务”和“按什么规则抽取”发生在两个不同步骤。当前函数签名为 create_tasks(document, provider="codex")，没有接收 Profile 参数。

下面是通用分支的等价展开写法，便于逐行读懂：

Python：任务生成解释
body = [s for s in document["spans"] if s["role"] == "body"]先选出正文 Span
tasks = []创建任务列表
for i in range(0, len(body), 6):每六个正文 Span 分成一组
task = {创建当前任务
"name": f"body-{i // 6:03d}",自动编号，如 body-000、body-001
"instruction": "Extract this profile's target claims from these evidence regions.",通用指令：从本次证据中提取 Profile 要求的知识
"spans": body[i:i + 6]本任务可使用的证据集合；最后一组可以少于六个
}任务对象只有名称、指令和证据三个主要字段
tasks.append(task)保存任务；还没有在此步读入 Profile 内容

3.3 任务分组与 Profile 约束在哪里会合

因此，Sun 运行的是：通用证据分组 + 新 Profile 约束下的抽取。模型在请求中读到新三件套后，按其中的六类实体和三类关系生成候选。系统能够为其他论文生成任务，但目前还不会依据新 ontology 自动决定“哪些章节应做哪类任务、哪些表格应专项抽取、需要什么审计”。

适合汇报的表述：Wang 使用定制任务规划；Sun 验证了更换 Profile 后的正文关系抽取流程，尚未验证通用、理解 Profile 目标的任务规划器。

4. 模型输入：一个 Task 怎样变成 Request

下面对照当前 pipeline.py 的实际请求结构。左侧为 Python 构造表达式，不是独立 JSON 文件。

Python：request 的字段向 LLM 提供什么
"task": task["instruction"],当前任务的提取指令
"ontology_version": profile["version"],当前 Profile 版本；字段名不表示这里加载了正式 OWL ontology
"rules": profile["rules"],何时提取、何时不提取，怎样保留条件与不确定性
"vocabulary": profile["vocabulary"],当前可用实体、关系及其他定义
"output_schema": profile["schema"],返回候选必须遵守的结构
"evidence": [...]仅放入当前 Task 的证据对象；数组中的各对象使用下面五个字段
"source_span_id": s["source_span_id"],可引用的真实证据 ID
"page": s["page"],PDF 页序
"kind": s["kind"],文本或表格证据
"table_number": s.get("table_number"),表号；正文通常为空
"text": s["text"]本次允许使用的登记原文

Sun 的 body-000/attempt-01/request.json 中，ontology_version 实际为 silica-six-class-relations-0.1-draft，evidence 有 6 个对象，来自 PDF 第 1–2 页。这里绑定的是新 Profile，未发送 Wang 的三件套。

模型负责返回候选并选择 Evidence ID；后台根据 ID 回填登记文本和 PDF 位置。模型写出的 supports 是“这处证据支持什么”的说明，不是原文引句，也不是独立的支持性验证结论。

实际请求、原始回答和每次尝试分别保存。超时、格式错误或工具执行异常按失败记录，不能记作 claims=[] 的成功空结果。

6. 验证与输出文件：检查到了哪一步，去哪里看

6.1 当前检查的边界

检查层当前已实现不能据此认定
Schema / 类型必填字段、字段类型、关系枚举、domain / range 等科学含义必然正确
EvidenceID 存在、属于当前任务、版本匹配，并回填登记原文证据一定充分支持整条陈述
数值 / 单位对结构化测量检查允许单位、raw 与 value、证据中是否出现数值等已排除所有表格串行、归属或计算口径错误
不确定性对提出机制的 modality、缺失条件状态等做已定义的检查已自动判断所有观察、解释和机制的科学类别
Wang 专项审计Table 3 预期 42 项逐项匹配全文提取完整，或其他论文也有同等专项检查
人工审核提供接受、拒绝、暂缓和单独正式发布的入口本轮已自动获得专家批准

因此，validated 文件名表示经过当前验证器处理；其中还要看 demo_eligible、blocking_errors、审核状态和语义状态，不能把文件中的所有记录统称为“已确认知识”。

7. 从开发参考案例到通用 Pipeline：仍需改进什么

7.1 当前“Benchmark”的定位

Wang 已打通“PDF → 证据 → 候选 → 工程检查 → KG → 原文核验”的参考流程；Sun 进一步跑通了另一篇论文和另一套 Profile。这里先把 Benchmark 理解为可复现的开发参考案例。目前尚无独立人工 Gold，不能报告正式测试集准确率。

现有主要边界：固定双栏解析、按字符切块、Wang 专用表格与任务、有限科学验证，以及尚未实现的通用任务规划。Sun 成功说明通用正文分支能够执行，并不证明所有版面、表格和图片都能可靠处理。

7.2 图片处理要区分三类任务

当前不从图像像素估读精确数值。理解图片表达的内容与恢复图中数值是不同任务。

图片类型例子后续可能的处理路线应保留的信息
Curve / Plot速率随时间、pH 的曲线识别坐标、单位和图例，再进行 Chart Digitization近似值、坐标来源、提取方法和误差
Schematic反应机制、实验流程示意图本地 VLM 理解对象、步骤及关系图号、Caption、解释范围和不确定性
Scientific ImageSEM、TEM、表面形貌VLM 辅助理解；尺寸或颗粒统计另需专用分析图像区域、比例尺、测量方法和不确定性

共同前提是 Figure Detection 和 Caption Association；得到 Structured Figure Evidence 后，再进入候选抽取与验证。以上均为后续计划，尚未在本轮实现。
